# Decision 为什么判断不了「做完没有」和「别再回去了」（2026-10-14）

源头是用户的问题：「我想研究一下为什么判断不了这个事情」。下面的试验全部打真实 Decision 服务（`h2oai/h2o-lightning-4b`），题面是真实运行里记录的原题，每次只改一个因素。脚本在 `bench/why-shown-probe*.py`、`bench/why-resume-probe*.py`、`bench/step2-progress-wording-trial.py`；输出在 `MineBot-always-on/logs/why-*-20261014.*`。

## 1. 服务本身：只有一遍打分，没有推理

- 每次请求都是 `tier=fast`、`passes_per_decision=1`、`output_tokens=0`。选项概率来自对每个选项的直接打分（`probability_source: native`），中间没有任何推理。
- 请求里的 `effort` 字段只接受 `fast` / `balanced` / `thorough`。后两个虽然收下，但响应注明「accepted for API compatibility but not implemented」，实际仍按 `fast` 跑。换句话说，没有「让它多想一想」的档位可调。
- 同一次请求里的几道题是分开打分的：「是否已显示」这道题单独问和与 q 一起问，概率完全相同。

## 2. 「做完没有」：会比较数字，但只在条件干净时

用 `ae4318a` 那次运行里误停的原题（意图「累计 4 个原木」、背包原木 3），把背包数量从 0 扫到 10：

| 条件 | 「已显示」概率随数量 0→10 的变化 | 结论 |
|---|---|---|
| 原题 | 0.39、0.77、0.71、0.67、0.82、0.56、0.51 | 和数量无关 |
| 只留意图 + 背包 + 主手，意图用中文「累计4个原木」 | 只在原木为 3 时最高（0.76） | 像在匹配字面，没在比较大小；「原木」对不上 `oak_log` |
| 只留意图 + 背包 + 主手，意图写成「at least 4 oak_log」 | 0–3 为 0.05–0.19，4–10 为 0.78–0.85 | **能比较** |
| 同上，目标改成 2 | 0、1 为 0.05；2、3、5 为 0.94 | **能比较** |
| 英文意图，但用完整题面 | 1–3 为 0.65–0.74，又判错 | 完整题面里有干扰 |

逐条消融（英文意图、原木 3）：

- 去掉进度行：0.65 → 0.21，答对。
- 最小题面加回进度行：0.19 → 0.75，答错。
- 其他每一条事实加入或去掉，影响都很小，包括写着 `count=4` 的当前工作。

进度行写的是「last progress event: inventory, 0.7s ago. inventory changed: oak_log +3」。模型把「背包刚刚变了」读成了「结果已经达成」。主手这一项它读得到：同一帧把主手从花岗岩换成石镐，「已显示」从 0.40 升到 0.84。

**为什么离线看着准、真实运行还是误停。** 两次运行里抽 159 个能标注的帧，意图未满足的 264 次判断中，现写法只误答 3 次（约 1%）。但这个问题在工作进行中每秒问一次，任何一次答「已显示」都会立刻结束工作。一次调用要问 30–60 帧，1% 的单帧错误累积下来，误停就很常见。真实运行 7 次停下里 3 次误停，就是这么来的。单独去掉背包增量那句，误答从 3 次降到 1 次。增量换个说法放进背包行或进度行，反而更差（13 次、29 次）。

## 3. 「别再回去了」：次数不进入判断

第 3 步那 5 帧（同一件工作被水打断 1–5 次，背包始终是 leaf_litter 1），每帧 6 种选项顺序：

| 写法 | 「叫 Agent」概率，被打断 1→5 次 | 结论 |
|---|---|---|
| 原题（5 句长记录） | 0.20、0.18、0.18、0.20、0.21 | 和次数无关 |
| 只留最少上下文，或压成一句汇总 | 0.11–0.28，都是平的 | 和次数无关 |
| 把次数写进「回去」这个选项 | 0.21 → 0.29，从不过半 | 几乎无关 |
| 选项里写次数，题面也写汇总 | 0.59、0.54、0.53、0.53、0.51，全选叫 Agent | 跟着措辞走，次数越多反而越低 |
| 单独问「之前回去有没有做成什么」 | 5 帧都答「什么都没做成」 | 话本身对，但第 1 次还没回去过，分不出该不该回去 |

## 4. 结论

这个 Decision 是一遍打分的小模型。它对**选项的字面**和**题面里的醒目线索**反应很强，对需要计数或比较的事实反应很弱。只有在题面很干净、名字完全一致时（英文物品名对英文背包），它才比较得准。改措辞的结果往往是所有帧一起翻，而不是按事实区分。

可选方向（都要用户定，下面只列事实依据）：

1. **单独发一个小请求问「做完没有」**，只带判断用得到的事实（意图、背包、主手；移动类意图加位置）。依据：最小题面配英文意图时，判断阈值清楚。代价是每帧多一个请求，约 80–150 ms。
2. **让 Agent 写意图时用身体事实里的物品名**（英文 ID）。依据：中文「原木」对不上 `oak_log`。这会改变给 Agent 的意图约定。
3. **带数量的工具在运行中不判做完**，到数由工具自己结束，结束后的结果题只判一次。依据：误停来自每秒都问。这会改变核心理念里「谁判断够了」的分工。
4. **「一再回到危险里」**：目前没有任何写法能让它按次数改变选择。可能的方向是在问之前减少它要做的推理：例如把「同一件事又被同一种危险打断、背包没变」作为身体如实记录的事实单独列出；或者把这类决定交给 Agent。用户已定不按次数由程序叫 Agent，这一条需要重新讨论。
